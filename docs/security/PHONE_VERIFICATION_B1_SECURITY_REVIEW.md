## 3. Trust boundary, secrets and rotation

```text
Browser ──(session)──▶ Server action ──▶ service.ts ──▶ PostgREST (service_role) ──▶ Postgres authority
                         authenticates      generates code (CSPRNG)                     stores ONLY HMAC + kid
                         the user           MAC = HMAC(key[kid], ctx+code)              owns every state transition
                                            hands code to delivery adapter              and the completion write
```

* **The database never sees the code or the key.** A database read (backup, replica, SQL injection, log) therefore cannot be turned into an offline brute force of a six-digit code — A2's finding that a salted SHA-256 would allow exactly that is closed.
* **The server never decides truth.** Limits, binding, single-use and the `phone_verified_at` write live in the database. The server is only ever given a user id it authenticated; the action accepts **no** user id, number or "verified" flag from the client.
* **MAC context** = `otp1|challenge_id|user_id|purpose|code` under a per-purpose subkey (`HMAC(key,"aladdin.phone-otp.v1")`). `computeMac` **throws** unless ids are UUIDs and the code is digits, so the `|`-joined encoding is injective by construction (a test found the original lacked this; §9 F3).
* **Client addresses** are never sent: the server sends `HMAC(subkey "aladdin.phone-ip.v1", ip)`; the address source is `cf-connecting-ip` only — a client-supplied `X-Forwarded-For` is ignored.
* **Keyring** `PHONE_OTP_HMAC_KEYS = {"current":"k2","keys":{"k2":…,"k1":…}}`, ≥32 random bytes each, ≤3 keys, validated at startup, error messages never contain key material. Parse failure ⇒ the feature refuses (fail closed, no default key).
* **Rotation runbook:** (1) add the new key beside the old, (2) make it `current` — new challenges use it, `verify` offers a MAC for every accepted kid so in-flight challenges still verify, (3) wait one challenge lifetime (≤10 min, default 5), (4) remove the old kid. A challenge whose kid was retired fails closed and costs the user one attempt (tested, `B1-rot-1…3`). IP buckets restart on rotation, which only ever loosens a limit for one window.
* **Compromise of the HMAC key** lets an attacker who *also* reads the challenge table compute codes offline for open challenges (≤5 min, ≤5 attempts online). Mitigate by rotating and purging. The key is never in the database, a log, `NEXT_PUBLIC_*`, or the repository.
* **Delivery adapter:** `PhoneOtpTransport.send({to, code, ttlSeconds})`. B1 wires only `disabledTransport` (throws) and an in-memory fake. The Cloudflare Worker stays a **pure delivery adapter**: it receives (destination, code), holds no proof state, and is never an authority. Plugging it in is a separate, approved change in `runtime.ts`.

## 4. Concurrency review: locks, isolation, ordering

**Global lock order (every B1 function):**

| # | Lock | Why here |
| --- | --- | --- |
| 1 | per-user advisory `aladdin.phone_verification.user:<id>` | serializes start/verify/invalidate for one account |
| 2 | `profiles` row `FOR UPDATE` | the **same first lock `profile_set_phone` takes**; freezes the number for the transaction |
| 3 | challenge row `FOR UPDATE` | single-use commit point |
| 4 | IP bucket upsert | leaf, always last, so a hot IP can never sit between two other locks |

* **The phone advisory lock (`app.lock_phone`) is deliberately not taken.** `profile_set_phone` locks the profile row first and the claim trigger takes the phone lock after; taking it before the row would invert that order. The profile row lock already pins the number, which is all verification needs.
* **Isolation:** `READ COMMITTED` (PostgREST default). After waiting on a `FOR UPDATE` the row is re-read, so the compared number is the committed one. Under `REPEATABLE READ`/`SERIALIZABLE` a concurrent change surfaces as `40001` and fails closed.
* **No stale verified state** — the completion statement is `UPDATE profiles SET phone_verified_at = now WHERE user_id = $u AND phone_e164 = challenge.phone AND phone_verified_at IS NULL` under the profile row lock, and raises (rolling back everything) if it matches no row.

| Interleaving | Outcome | Proven by |
| --- | --- | --- |
| verify ∥ verify (same code) | exactly one `verified`, one audit event | `B1-con-1` (8 parallel) |
| verify ∥ phone change, change first | verify finds a different number ⇒ `invalid`, nothing verified | `B1-con-3`, pgTAP E2–E4 |
| verify ∥ phone change, verify first | change waits, existing `profiles_reset_phone_verification` sets `phone_verified_at` back to NULL | `B1-con-3` (14 trials, both orders), pgTAP E10 |
| verify ∥ unrelated profile update / same-number re-save | verification lands | `B1-con-4` |
| start ∥ start | exactly one challenge, rest rate-limited | `B1-con-2` (8 parallel) |
| start ∥ verify (supersede) | never "verified **and** an open challenge" | `B1-con-6` |
| start ∥ phone change | any open challenge is for the number held now | `B1-con-5` |
| phone-change journal pending / needs_attention | start & verify refuse | pgTAP E12–E13 |
| trigger disabled, number changed mid-flight | verify itself re-checks the live number | pgTAP E5–E9 |

* **Deadlocks:** `pg_stat_database.deadlocks` delta is **0** across all race scenarios (`B1-con-7`).
* **Mutation testing** (local DB, then reset): removing the live-number check ⇒ pgTAP E7/E8 fail; removing the profile row lock ⇒ **2 deadlocks** in the race suite; removing the per-user lock in `verify` ⇒ **no test fails (survived)**. That lock is belt-and-braces: `start` and `verify` already serialize on the profile row. It also covers `invalidate`, which takes no profile lock, and it keeps the documented order uniform — it is not load-bearing for the tested interleavings and is not claimed to be.
* **Pre-existing, not B1:** `secondary_phone_make_primary` takes *phone-user advisory → reservation → phone advisory → profile row* while `profile_set_phone` takes *profile row → phone advisory*. Two concurrent operations by the **same account** could deadlock (PostgreSQL aborts one; no inconsistent state). B1 neither relies on nor changes this; flagged for a separate fix.

## 5. Limits and non-enumeration

| Control | Value (config row, CHECK-bounded) | Tested |
| --- | --- | --- |
| Code | 6 digits, CSPRNG, uniform | unit |
| Lifetime | 5 min (1–10) | pgTAP C6, D17 |
| Attempts per challenge | 5 (1–10), then dead | D3–D14 |
| Resend cooldown | 60 s | F1–F3, `B1-lim-1` |
| Per-account starts | 6/hour, 10/day | F7–F11, `B1-lim-1` |
| Per-IP-key starts | 20/hour | F12–F15 |
| Per-IP-key failed verifies | 30 / 15 min, refusal burns **no** attempt | F16–F18, `B1-lim-2` |
| One open challenge per account | partial unique index | F6, `B1-con-2` |
| Replay | consumed challenge ⇒ `invalid`, still one audit event | D1–D2, `B1-*-6` |

Every verification failure — wrong code, another account's challenge, unknown id, expired, consumed, invalidated, number changed — is the single answer `invalid`, with no ownership or state hint (D16 shows an unknown id and another account's id are byte-identical). `rate_limited`/`unavailable` concern only the caller's own IP/feature state. Errors never carry the number, a code or a MAC.

## 7. Verification grants nothing else

The completion write touches `profiles.phone_verified_at`. Checked: no Auth user gained `phone`, no non-email identity or MFA factor exists, no RLS policy depends on `phone_verified_at` (so it cannot gate access), no other function writes it (pgTAP H5), `service_role` holds no direct UPDATE on the column (A2 `FORGE-4`; the definer function is the only writer), and a verified number is not accepted as a GoTrue credential. No consent receipt changes (consents snapshot identical). Nothing in recovery or MFA reads this column; both remain separate flows.

## 8. Privacy: controls added and recommendations

**Implemented in B1:** the database stores the MAC and key id, never the code; client addresses only as HMACs; audit rows carry `{purpose, channel}` only — pgTAP C18 and `B1-priv-1` assert no number, code or MAC; a retention function `phone_verification_purge` (≥1 day, default 30) removes closed challenges (each carries a phone number) and stale IP buckets; the log scan (`B1-priv-2`) finds no raw code, no MAC and no non-alias number in GoTrue, PostgREST, gateway or database logs.

**Existing phone-bearing data** (catalog inventory of columns named like phone/e164/alias/whatsapp): `profiles`, `secondary_phone_reservations`, `phone_cooldown_overrides`, `app.installer_phone_changes` (old and new number **and alias**), `app.installer_alias_exceptions`, `organizations.contact_phone`, `organization_contacts`, `customers`, `network_*`, `assignment_contacts`, `job_work_contacts`, `onboarding_progress`, `organization_invitations`, `business_creation_drafts`, `admin_cases`, plus the new `app.phone_verification_challenges`.

**Recommendations (not implemented; each needs an owner decision):**
1. **Phone-bearing aliases (A2 finding S3).** An alias is `p<digits>@craftsman-login.aladdin.invalid`, and GoTrue prints the account email in `user_signedup`/`login` events, so these numbers are in GoTrue logs. **Do not rewrite existing aliases** — that changes a login identity and violates the invariance requirement. Instead: (a) treat Auth/GoTrue logs as personal data — restrict access, set short retention, and never forward them to a third-party drain without filtering `email`/`actor_username`; (b) for **new** phone sign-ups (Phase B2), derive the alias from `HMAC(secret, e164)` rather than the digits, so a log line no longer reveals the number while sign-in stays deterministic; (c) keep legacy aliases until accounts naturally migrate.
2. **Audit log** is append-only by design (it blocks deleting any audited account), so it must never receive a number. Keep B1's rule (`{purpose, channel}` only) and add a CI assertion that no audit action's metadata matches a phone pattern.
3. **Journal and cooldown tables** hold old/new numbers; give them a retention policy like the challenges.
4. **Schedule `phone_verification_purge`** before enablement (no scheduler is configured; deployment blocker §11).
5. **Never log the dev OTP or the HMAC key**; the fake transport is the only place a code exists in tests.
